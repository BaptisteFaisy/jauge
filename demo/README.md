# Demo environment — synthetic traffic and offline seed

This package holds the **demonstration environment** described in §18.1 of the
specification: three client applications at customer A, one at customer B, and
**no real data at all**. Everything — prompts, answers, token counts, latency,
billed amounts — is generated by the code in this package, deterministically,
from an explicit seed.

Nothing here calls AWS, HTTP or an LLM. The demo runs offline on a laptop.

```
demo/
├── profils.py        traffic profiles (volumes, hours, token ranges, service tier)
├── traffic.py        deterministic generator of Bedrock model-invocation logs
├── cur.py            CUR 2.0 line items, reconciled against the traffic
├── analyse.py        per-application statistics and lever detection
├── scenario.py       replay campaigns, recommendations, staged rollout
├── seed.py           `peupler_store` + `python -m demo.seed` console summary
├── socle.py          reloads the shared fixtures (tenants, apps, price table)
└── apps/             the customer applications + offline model client
    ├── port.py           `ModeleClient` port, request/response types
    ├── support_assistant.py
    ├── ticket_classifier.py
    ├── doc_summarizer.py
    ├── kb_search.py      customer B application (fleet view)
    └── fake_client.py    `FakeModeleClient`, offline and deterministic
```

## The scenario

### Customer A — `t-demo-a` (account `123456789012`)

| Application | Model | Profile | Cost lever it triggers |
|---|---|---|---|
| `support-assistant` | large | Long prompts (~1 960 input tokens), prose answers (~730 output tokens), high latency (~2.5 s p50), business hours | **Repeated requests**, **missing prompt cache** (one 620-token system prefix repeated on every call, zero cache-read tokens) and **errors/retries** |
| `ticket-classifier` | large (a smaller one would do) | Short prompts (~145 input tokens), short structured JSON answers (~17 output tokens), high volume | **Oversized model** (plus repeated identical requests and throttling retries) |
| `doc-summarizer` | large | Nightly batch, 01:00–04:00, **Standard** service tier, very long answers (~2 450 output tokens, p95 3 674 against a 4 096 limit) | **Deferrable workload** and **answers too long** |

### Customer B — `t-demo-b` (account `210987654321`)

| Application | Model | Profile | Purpose |
|---|---|---|---|
| `kb-search` | medium | Business hours, short answers | Fills the **fleet view** (two customers side by side) |

Volumes are deliberately small: the demo proves the mechanics, it is not a
production forecast. The monthly projection shown on screen is
`observed cost × 30 / days`, computed by the code.

## What each screen should show

Seed data covers the **14 last full days** ending on the profile's reference
date (`demo.profils.DATE_FIN_DEFAUT`).

1. **Cost attribution dashboard** — spend per application and per team,
   reconciled with the invoice. Expected on the default seed:
   - customer A total ≈ **$677 over 14 days**, i.e. **≈ $1,451 / month**;
   - `doc-summarizer` ≈ $345, `support-assistant` ≈ $301,
     `ticket-classifier` ≈ $31 for the period;
   - customer B (`kb-search`) ≈ $8.59 for the period, ≈ $18.41 / month;
   - reconciliation gap **< 1.2 % every day** (target is under 3 %), so every
     daily reconciliation reads *compliant* — 14/14 days, mean gap 0.57 %.
2. **Lever list** — eight levers detected, ≈ **$628.58 / month** of estimated
   savings in total: repeated requests ($76.32 + $11.68), missing prompt cache
   ($64.00), oversized model ($63.20), errors and retries ($4.88 + $1.34),
   deferrable workload ($369.72), answers too long ($37.44).
3. **Replay campaign on `ticket-classifier`** — 200 requests sampled (seed 42),
   replayed on the current model (reference, 100 % self-agreement) and two
   candidates. The medium model reaches **100 %** equivalence with a 95 %
   confidence lower bound of 98.1 % and zero deterministic failures: it clears
   the 95 % threshold at a 5× lower cost per request ($0.001100 → $0.000220).
   The small model reaches only 90.5 % (lower bound 85.6 %) with 19
   deterministic failures: rejected.
4. **Recommendation pending approval** — the passing candidate (medium model),
   ≈ **$17.04 / month** of expected savings, cost per request falling from
   $0.001100 to $0.000220, latency p50 from 387 ms to 424 ms. Status
   `PENDING_APPROVAL`, `approvedBy` empty: a human must approve.
5. **Rejected candidates on `support-assistant`** — no candidate reaches the
   application's 97 % threshold: the medium model stops at **94.0 %** (lower
   bound 89.8 %), the small one at **93.5 %** (lower bound 89.2 %) with 9
   deterministic failures. The recommendation is stored as `REJECTED` **with
   its evidence**, which is the point: the tool says no, and shows why —
   75.41 $/month left on the table rather than traded for a quality
   regression.
6. **Staged rollout in progress on `doc-summarizer`** — Standard → Flex on the
   same model, currently at the **50 %** step, online quality 0.995 against an
   alert threshold of 0.90, with the 30-day savings verification attached
   ($354.84 observed against $369.62 expected, 4.0 % gap).
7. **Fleet view** — both customers, spend and lever counts side by side. Tenant
   isolation is enforced by the store: customer B never sees customer A's
   applications, aggregates, levers, campaigns or recommendations.

### Using the seed from Python

```python
from jauge.store.memory import MemoryStore
from demo.seed import peupler_store, resume

store = MemoryStore()
peupler_store(store)  # 2 tenants, 4 apps, 14 days of aggregates, ...
print(resume(store))  # same summary as `python -m demo.seed`
```

`peupler_store` only uses the public `Store` protocol: it registers tenants,
applications, daily aggregates, daily reconciliations, levers, campaigns,
recommendations, a staged rollout and its savings verification. Swap
`MemoryStore` for any other `Store` implementation and the same code works.

Determinism: the default seed is `demo.profils.GRAINE_DEFAUT`. Passing another
seed to `peupler_store` / `generer_trafic` changes the traffic, never the shape
of the scenario.

### Generating traffic directly

```python
from demo.traffic import generer_trafic, lignes_cloudwatch
from demo.cur import generer_lignes_cur
from demo.seed import charger_socle_demo
from jauge.engine.calculator import TableTarifs

records = generer_trafic(graine=20261111, jours=14)  # list[JournalInvocation]
lignes = lignes_cloudwatch(records)  # Bedrock invocation-log rows
table = TableTarifs(charger_socle_demo().tarifs)
cur = generer_lignes_cur(records, table)  # CUR 2.0 line items
```

## Record formats

`demo/traffic.py` documents the exact invocation-log format it produces
(module docstring). `demo/cur.py` documents the CUR 2.0 columns. Both are
reproduced in the pull request description so the attribution module (M1) and
the reconciliation work can align on them.

## Privacy and data

- **No real data.** Every prompt, answer and document fragment is synthetic
  text written for the demo.
- Prompts and answers never leave the data plane in the real product; in the
  demo they simply never leave this package. The control-plane objects built by
  `demo.scenario` (recommendations, campaign results) carry **aggregates and
  identifiers only** — no request text.
- The two AWS accounts and ARNs are fictional placeholders.

## Tests

```bash

```

They cover: generator determinism (same seed ⇒ same records, other seed ⇒
different traffic), invocation-log format, realistic volumes and profiles
(classification far shorter than the assistant, summarization at night),
CUR-versus-recomputed gap under 3 %, store contents (2 tenants, 4 applications,
14 days of aggregates), tenant isolation, and the full scenario story.
